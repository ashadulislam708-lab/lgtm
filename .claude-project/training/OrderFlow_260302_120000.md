**8. What makes your app special:**
This is a backend API project designed specifically for testing LGTM (Loki, Grafana, Tempo, Mimir) observability stack. The API is intentionally designed with varying response characteristics:
- **Fast endpoints** (~10-50ms): Simple CRUD operations, health checks, product lookups
- **Medium endpoints** (~200-500ms): Order creation with validation, inventory checks
- **Slow endpoints** (~1-5s): Report generation, bulk operations, payment processing simulation
- **Error-prone endpoints**: Simulated failures for payment processing, stock checks, external service timeouts
- **Cascading service calls**: Order processing triggers payment → inventory → notification chain (ideal for distributed tracing)

## Features

**11. Main Features (per user type):**

### Customer
- Browse and search products (FAST - simple DB queries)
- Place orders (MEDIUM - validation + inventory check)
- View order history and status (FAST - indexed queries)

### Admin
- Manage product catalog with bulk import (SLOW - CSV/JSON parsing, batch DB writes)

- View system health and metrics dashboard data (FAST - cached metrics)

### System (Background)
- Payment processing simulation (SLOW - 1-3s external API simulation with retries)
- Inventory sync with external warehouse (SLOW - simulated external service with random latency)
- Order status change notifications (ASYNC - queued processing)
- Scheduled report pre-generation (CRON - heavy background job)

**12. Main Feature Module Flow:**

### Module: Product Catalog (FAST - target <50ms)
1. Customer/Admin sends GET /products with optional filters (category, price range, search term)
2. System queries database with indexed fields
3. System returns paginated product list with metadata
4. Logging: Request params, query time, result count

### Module: Order Placement (MEDIUM - target 200-500ms)
1. Customer sends POST /orders with product IDs and quantities
2. System validates product availability (DB query ~20ms)
3. System checks inventory levels (service call ~50-100ms)
4. System calculates pricing with tax (computation ~10ms)
5. System creates order record (DB write ~30ms)
6. System triggers async payment processing (queue push ~10ms)
7. System triggers async notification (queue push ~10ms)
8. System returns order confirmation with tracking ID
9. Logging: Full order details, each step duration, correlation ID
10. Tracing: Spans for each sub-step with parent-child relationships

### Module: Payment Processing (SLOW - target 1-3s)
1. System picks up payment job from queue
2. System calls external payment gateway (simulated 500ms-2s latency)
3. On success: Update order status to "paid", trigger inventory reservation
4. On failure: Retry up to 3 times with exponential backoff, then mark as "payment_failed"
5. System sends payment confirmation/failure notification
6. Logging: Payment attempt details, gateway response, retry count
7. Tracing: Full payment flow with external service span
8. Metrics: Payment success/failure rate, gateway latency histogram

### Module: Report Generation (SLOW - target 2-5s)
1. Admin sends POST /reports with report type and date range
2. System validates date range and report type
3. System executes aggregation queries across orders, payments, products (2-4s)
4. System formats report data (JSON/CSV)
5. System returns report or job ID for async retrieval
6. Logging: Query execution plan, row counts, total generation time
7. Tracing: Individual query spans within report generation

### Module: Inventory Sync (MEDIUM/SLOW - target 300ms-2s)
1. System calls external warehouse API (simulated, variable latency 200ms-1.5s)
2. System compares local stock with warehouse stock
3. System updates local inventory records
4. System logs discrepancies
5. Logging: Sync details, discrepancy count, external API response time
6. Tracing: External service call span with status

### Module: Health & Metrics (FAST - target <20ms)
1. GET /health returns service health status
2. GET /metrics returns Prometheus-compatible metrics
3. Includes: request count, error rate, response time histograms, active connections, queue depth
4. Logging: Minimal (avoid log noise on health checks)

## Observability Requirements (LGTM Stack)

### Logging (Loki)
- All logs in structured JSON format
- Log levels: DEBUG, INFO, WARN, ERROR
- Each log entry must include: timestamp, level, message, correlation_id, service_name, method, path
- Error logs must include: stack trace, request body (sanitized), user context
- Slow query logs: Any DB query taking >100ms should log at WARN level
- Request/response logging middleware with body capture for non-sensitive endpoints

### Monitoring (Mimir/Prometheus)
- RED metrics for all endpoints: Rate, Errors, Duration
- Custom business metrics: orders_placed_total, payments_processed_total, reports_generated_total
- Database metrics: connection pool usage, query duration histogram
- Queue metrics: depth, processing time, failure rate
- Runtime metrics: CPU, memory, event loop lag (Node.js specific)

### Tracing (Tempo)
- OpenTelemetry instrumentation for all HTTP handlers
- Automatic span creation for: HTTP requests, database queries, queue operations
- Manual span creation for: business logic steps within order processing, payment flow
- Context propagation via W3C Trace Context headers
- Span attributes: user_id, order_id, payment_id, endpoint_category (fast/medium/slow)

### API Response Time Design

| Endpoint Category | Target Latency | Endpoints | Purpose for Testing |
|-------------------|---------------|-----------|-------------------|
| **Fast** | <50ms | GET /health, GET /products, GET /products/:id, GET /orders/:id | Test baseline metrics, normal trace patterns |
| **Medium** | 200-500ms | POST /orders, PUT /products/:id, GET /orders (with filters) | Test moderate latency traces, multi-span operations |
| **Slow** | 1-5s | POST /reports, POST /products/bulk-import, POST /inventory/sync | Test slow query detection, timeout handling, long traces |
| **Error-prone** | Variable | POST /payments/process (20% failure rate), POST /inventory/sync (10% timeout) | Test error logging, retry traces, circuit breaker metrics |
| **Async** | N/A (queued) | Order notifications, payment processing, inventory sync | Test async trace linking, queue depth monitoring |

### Simulated Failure Scenarios
1. **Payment gateway timeout:** 10% of payment calls take >5s and timeout
2. **Payment gateway error:** 10% of payment calls return 500 error
3. **Inventory service degradation:** Randomly adds 500ms-2s extra latency
4. **Database slow query:** Report queries intentionally use non-optimal patterns
5. **Memory pressure:** Bulk import endpoint processes large payloads
6. **Queue backup:** Simulate slow consumer causing queue depth increase
